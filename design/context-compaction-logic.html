CONTEXT COMPACTION

Agent 聊天的「上下文回收站」

Agent 多轮 ReAct 循环中消息会无限增长，撞上 LLM 128K 上下文窗口就 400。 本项目用一套纯规则（零 LLM 参与）的压缩体系：预剪枝改写老工具结果 → 按尾部预算丢弃早期消息 → 注入压缩提示，同时保证 tool_calls/tool 配对合法、 内存 / DB / LLM 视图三者一致、UI 可感知可还原。

01这套体系解决什么问题

四条硬约束，决定了它不是简单地把数组截断。

① 不能撞窗口② 不能切断工具配对③ 内存 = DB = LLM 视图④ 压缩本身不调 LLM

AgentLoop 每轮调用 LLM 前检查消息总量，超阈值就执行压缩。压缩器 ContextCompactor 是纯函数：输入消息列表，输出压缩后的消息列表 + 元数据，自己不发任何 LLM 请求（P2 规划中的 LLM 摘要除外）。 之所以要配对保护：OpenAI 兼容网关要求每条 role:"tool" 消息前面必须有声明对应 tool_calls 的 assistant 消息，切断了直接 400。

压缩的落库遵循 v32 统一历史模型：DB 的 chat_messages 表 1:1 存 agent 消息， 压缩后以内存为基准用 replaceMessages 单事务原子重写 DB，跨会话永不「复活」已压缩内容。

03何时压缩：四条触发路

AgentLoop 每轮 LLM 调用前检查一次。有真实 usage 时直接对照 token 阈值；没有时双轨启发式兜底。

PATH 1 · 最准
真实 promptTokens
上一轮 LLM 末帧 usage 回报的 prompt_tokens 被动记录，下一轮直接对照 token 阈值，绕过一切估算。
usage.promptTokens ≥ 100K → 压缩
PATH 2 · 字符启发式
字符总量阈值
消息总字符（content + toolCalls 参数 + toolCallId）≥ 500K 字符，约等于 125K tokens。
totalChars ≥ 500,000 → 压缩
PATH 3 · token 启发式
CJK 加权估算
无 usage 时按 CJK 字符 ×2、其他 ×0.25 估算 token（准确度约 80%，比纯字符准）。与 PATH 2 任一超限即触发。
estimatedTokens ≥ 100K → 压缩
PATH 4 · 强制
finish_reason = length
输出被截断往往意味着上下文压力，置 _forceCompaction 标记，下一轮无条件先压缩（content_filter 不触发）。
finishReason == 'length' → 下轮强制

两个防呆细节

空压缩跳过：如果压缩结果「丢弃 0 条且无改写」（比如首轮就撞 length），不 apply、不 emit 事件， 避免往上下文和 DB 里插一条「丢弃 0 条」的无意义压缩提示。
思维链不入账：reasoning 增量只 emit 给 UI 展示，从不写进消息历史，自然也不参与压缩。

Step 1 · P1 预剪枝

对「可改写区间」（去掉最近 6 条 tool result 后的历史区）的老 tool result 改写 content： Pass 1 MD5 去重 + Pass 2 按工具类型 1-liner 摘要。只改 content，不动 toolCallId / 顺序 / 配对。

Step 2 · 边界选择

从最后一条向前累加字符，超过 preserveTailChars（100K）处为候选切点； 若保留段首条是 tool 消息，逐条向前回退到其归属 assistant——多保留一条是安全方向，留下孤儿才会 400。

Step 3 · 重组

最终消息列表 = [system prompt] + [压缩提示] + [保留尾部]。 压缩提示是带 KV 前缀的 system 消息：KV 给解析器还原 UI marker，自然语言给 LLM 看。

压缩提示长这样

[上下文压缩|droppedCount=8|keptCount=2|removedChars=14500|originalChars=22800|compactedChars=8300|rewrittenCount=3|timestamp=1763160000000]
早期 8 条消息已被压缩移除。请基于保留的最近 2 条消息继续对话。如果缺少关键信息，请使用工具重新查询。

05预剪枝细节：去重与 1-liner

小说场景里工具结果最占空间（整章正文几千字），而 LLM 对「很久之前读过什么」只需要一行记忆。

Pass 1 · MD5 去重

区间内 content > 200 字符的 tool result 两遍扫描：第一遍记录每个 MD5 的最后出现索引， 第二遍把非最后出现的重复替换为指向标记——保留最新原文，旧的变成「这里有过一份相同结果」的指针。 200 字符以下的短结果不参与（两条 "OK" 碰巧相同不该被去重）。

#7 · read_chapter_content（6500 字，与 #5 内容相同）第三章全文……
→
"[read_chapter_content dup of 5#a3f9c1]"

Pass 2 · 按工具类型 1-liner

未被去重的、content > 500 字符的结果改写成一行结构化摘要。短结果不动（改写收益低、信息损失大）。

read_chapter_content · 纯文本第三章 夜渡 ……（6500 字正文）
→
[read_chapter] 6500 字
list_chapters · JSON{"count": 42, "chapters": [……]}
→
"[list_chapters] 42 章"
search_in_chapters · JSON{"keyword":"主角","totalChaptersHit":12,"totalMatches":37, ……}
→
"[search] 搜\"主角\" 命中 12 章/37 处"
execute_js · JSON{"__meta":{"run_id":"…","mode":"extract"}, ……}
→
"[execute_js] extract r-a1b2c3d4"
未知工具 · fallback（任意长内容）
→
"[toolName] (N 字符)"

红线：改写只作用于 tool result 的 content。assistant 的 toolCalls（含 arguments，LLM 决策上下文）、 user / system 消息、toolCallId、消息顺序与配对关系一律不动。错误分支（含 error 字段）保留 error / message 原文。

06一致性同步：内存 / DB / LLM 视图

v32 起 DB 直接 1:1 存 agent 消息，压缩后的回写以内存为基准原子重写，三个视图永不分叉。

CompactionEvent 到达后，ScenarioSessionChain._handleCompaction 依次执行：

// 1) 内存裁剪：丢掉前缀 [0, cut)
_agentMessages.removeRange(0, removed);

// 2) 头部插入压缩提示（独占 index 0，落库即 agentMsgIndex=0）
_agentMessages.insert(0, ChatMessage(role: 'system', content: e.compactionNote));

// 3) 应用预剪枝改写：压缩前 index → 落点 = index - cut + 1（+1 为头部 marker 占位）
//    落在丢弃段（index < cut）的 entry 已随 removeRange 消失，无须处理
//    （历史 bug 备注：曾误用 `- cut`，改写落到前一条消息上——已修复 +1）

// 4) DB 原子重写：以当前内存为基准，replaceMessages 单事务整段重写
unawaited(_persistence.rewriteAgentMessagesInDb(cut, logTag: 'compaction_db'));

重启或切会话时 hydrate 从 DB 读回消息：压缩提示 system 消息保留在 agent 消息序列里（LLM 下一轮仍能看到）， UI 投影层则用 CompactionNoteParser 识别 KV 前缀，把它渲染成 marker 卡片而不是一条灰 system 文本。

08参数速查表

全部集中在 CompactorConfig，可整体关闭（enabled: false）。

参数默认值作用
maxContextChars500,000字符阈值（≈125K tokens），适配 GPT-4o / DeepSeek / Qwen 的 128K 窗口，留 28K 给输出 + 新消息
maxContextTokens100,000token 阈值；有真实 usage 时优先对照它
preserveTailChars100,000尾部保留预算（≈25K tokens，占总阈值 20%），保证近期对话 + 工具结果不丢
protectRecentToolResults6最近 6 条 tool result 免改写（≈3 轮调用），LLM 下轮可能还追问
dedupThresholdChars200content 超过此值才参与 MD5 去重（防误判短结果）
longFieldChars500content 超过此值才被 1-liner 改写
prePruneEnabledtrue关闭则退化为 v32 的「按切点丢弃式」压缩
ToolResultFormatter.maxChars50,000上游防线：实时工具结果回传时截断，加 "... [truncated]" 后缀

09设计边界与演进方向

当前边界

· 1-liner 是规则式摘要（数 count / 拼关键字），不是语义摘要——LLM 只知道「读过 6500 字」，不知道读了什么。
· 丢弃式压缩不生成「前情提要」，早期对话细节丢失后只能靠工具重查（压缩提示里正是这么引导 LLM 的）。
· 压缩只在主 Agent 的 session 链上发生，子 Agent 的 CompactionEvent 是 no-op。

P2 规划（代码内注释已标注）

用 LLM 生成结构化摘要替代规则式 1-liner。预剪枝层是它的前置：先把总字符数降下来， 减少需要送去做 LLM 摘要的内容量。届时压缩将分两级：廉价规则剪枝（每次都跑）+ 昂贵 LLM 摘要（必要才跑）。
