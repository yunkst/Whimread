一句话版本

番外是一本不入书架的迷你小说：有自己的章节列表与完整阅读体验，挂载在某个锚点章之下，可无限递归。创作直接发生在主聊天里——主聊 Agent（34 工具全集）本就带着这本书的上下文（聊过的剧情、读过的章节、人物卡），用 create_side_story 定位番外写入目标、逐章「回复中写全文 + save_side_story_chapter 落库」即完成创作，落库前过五道防线。工作小说全程保持宿主不变：读/搜/人物卡天然指宿主（查证通道），写番外走显式工具（写通道），读写硬分离。

01

入口：两条路，一个目的地

无论从哪里发起，最终都是主聊 Agent 在同一个对话流里用同一组番外工具完成创作。

路径 A · 番外弹层（UI 表单）
阅读器顶栏「番外 N」角标 / 右上菜单「本章番外」
目录页章节行「番外 N」徽标 / 菜单「番外列表」
→ 本章（或小说级）番外列表页 → 底部「创建番外」
→ 弹层表单：锚点章只读展示 + 需求描述（必填） + 期望章节数（可选）
提交 → 打开主聊对话窗自动发送创作请求 → 逐章生成实时可见

锚点章由入口天然确定；弹层提交时会把阅读上下文对齐到锚点章，Agent 的 create_side_story 自动定位。主聊有任务在跑时请求预填输入框不并发注入。

路径 B · 主聊天一句话
「给这一章写个番外，讲讲女主的童年」
主聊天 Agent 识别番外意图 → 先查证主线相关事实（读章/搜索/人物卡）
调用 create_side_story(title, requirement)
直接在本对话逐章创作：写全文 → save_side_story_chapter × N

锚点章 = 用户当前正在阅读的章节；非阅读态时 Agent 引导先打开目标章节，或按用户指定的章节序号传 anchorChapterPosition。对话历史不切换、上下文不丢失。

02

番外工具三件套：主聊里的读写分离

番外创作并入主聊（writing 场景，34 工具全集）后，专用工具只剩三个，职责极窄：一个定位写入目标、一个显式写番外、一个只读盘点。其余全部复用主聊既有工具。

🔖 create_side_story 幂等

titlerequirement?anchorChapterPosition?

建隐藏行（不入书架）。锚点自动取当前阅读章（在番外章节内阅读时 novelUrl 即父番外 → 递归免费）；非阅读态可传当前小说章节序号。同锚点 + 同需求重复调用幂等找回已建番外——续写、进程重启恢复都靠它。

✍️ save_side_story_chapter

positiontitle?content

显式写番外命名空间（与 save_chapter=正篇 在命名上分开）。复用五道落库闸门；结果携带 sideStoryChapterCount 供 Agent 校准下一章 position。无写入目标时返回 no_side_story 引导先 create。

📋 list_side_stories

（无参数）

只读盘点当前小说的全部番外（标题/章数/字数/锚点章/需求），供回答「有哪些番外」与避免重复创作。

1

写入目标怎么跨回合保持（select_novel 同款机制）

create_side_story 成功 → 工具结果 JSON（sideStoryId/sideStoryUrl/sideStoryTitle）→ 会话监听 ToolCallEndEvent 解析并记录写入目标 → 之后每轮构造上下文自动注入，save_side_story_chapter 据此落库。进程重启丢内存态后，Agent 重调 create（幂等查库）自动找回，不丢不重。
2

为什么 currentNovel 不切换

主聊的一致性约定是「工具作用于当前小说」——保持宿主不变，read/search/list_chapters/list_characters 天然就是查证通道；番外写入走显式工具（save_side_story_chapter 内部自己构造指向番外的上下文），两个通道硬分离，Agent 无需在两本书之间来回切换。
v1 → v2 架构变更说明：此前番外由独立 side_story 场景（专用锁定工具面）+ 跨场景移交（start_side_story → 换会话干净开始）完成。v2 按用户判断「番外作为全新上下文不合理，应让主 Agent 直接写」重构：删除独立场景与移交机制，主聊上下文（聊过的剧情、读过的章节）全程复用，实现面净简化。存量 side_story 会话按 writing 场景兼容构建，可继续对话。
03

创作流程：主聊内一章一轮（系统提示词强约定）

番外并入主聊后，Agent 用主聊全量工具创作——查证用宿主通道，写入用番外工具，一章一轮。整个流程发生在用户的既有对话流里，上下文不切换。

1

查证主线相关事实 防创作歪的关键步骤

涉及人物在锚点章之外有戏份 → read_chapter_content(position) 读相关章节或锚点前后相邻章；具体事实（口癖/旧伤/关系变化/道具/时间点）→ search_in_chapters 按关键词查证；人物卡 → list_characters；写作技巧 → list_prompt_tags / get_prompt_tag。凡引用主线既有事实，先查证再落笔。这些工具全部作用于宿主——currentNovel 不切换，查证零成本。
2

建番外 幂等

create_side_story(title, requirement)：锚点自动取用户当前阅读章；同锚点 + 同需求重复调用幂等找回已建番外（续写/重启恢复都靠它，绝不重复建）。标题像作品名（4~10 字）。requirement 忠实转述用户需求——它同时是番外描述与幂等键。
3

逐章创作（一章一轮）

在回复中直接写出该章完整正文（1500~3000 字），写完立即 save_side_story_chapter(position, title, content)，content 与回复正文逐字一致。position 从 1 连续递增，用结果里的 sideStoryChapterCount 校准下一章；一轮只写一章、保存一章。人物细节前后一致，章尾留推进感。
4

收尾总结

全部保存后输出简短总结（番外名/章数/各章一句话简介），不再调工具——流程结束，对话窗出现「查看番外」「查看新保存的番外章节」跳转卡。
为什么「正文写在回复里」：这是 2026-11-14 的架构重构（save_chapter 取代旧 create_chapter 的独立 LLM 调用）。旧方案只靠一句 instruction 传上下文——细节错乱的根源。现在正文与锚点章、人物卡、聊过的剧情、已写章节共享同一份主聊上下文，一致性由会话记忆保证。
04

Agent 上下文管理策略

Agent 能写对的前提是「看得见」。上下文分五层来源，各自的生命周期与管理方式不同——番外创作的正确性取决于第 3 层的查证纪律与读写分离。

五层上下文来源（全场景通用）

层内容生命周期
① system prompt 场景身份 + 工作流程 + 硬性规则（主聊另有番外指引：意图识别 → 查证 → create → 逐章 save_side_story_chapter） 每次会话静态注入，永不压缩
② user 前缀注入 每条用户消息头部自动携带：正在阅读《》· 章节 / 当前工作小说（阅读器实时状态） 随消息持久保留
③ 工具拉取 读章节正文 / 全文搜索 / 人物卡 / 大纲 / 已写章节——Agent 主动决定看什么，结果进会话历史 会话内保留，受压缩器管理
④ 经验记忆 agent_memories 表：跨会话沉淀的写作经验 持久，每次会话注入
⑤ 上下文压缩器 超出阈值后的自动瘦身（详见下） 按需触发

番外创作期间，上下文发生什么（不换会话）

用户在主聊天里说「给这一章写个番外」——不再切换会话、不再丢历史。变化只有一处：会话里多了一个「番外写入目标」。

时机上下文变化
创作开始前无变化——主聊已有的对话历史（聊过的剧情、此前的问答）全部在场，这正是主聊创作上下文更充实的来源
create_side_story 成功会话记录「番外写入目标」（番外 id/url/标题，仿 select_novel 的状态接线）；此后每轮上下文自动携带。currentNovel 保持宿主——读/搜/人物卡全部继续指宿主
逐章创作中每章：Agent 回复（全文）→ save_side_story_chapter 工具结果（元信息）→ 追加进会话历史；已写章节自然留在上下文里，前后衔接靠会话记忆
进程重启 / 长会话压缩若写入目标丢失，Agent 下次 save 收到 no_side_story → 重调 create_side_story → 幂等查库找回（锚点+需求），不产生重复番外
创作结束后写入目标保留在会话中（用户说「番外再加一章」可直接续写）；主聊继续正常问答/改文，save_chapter 照旧写正篇——两把钥匙各开各的门

上下文压缩器（长会话的瘦身机制）

机制行为
触发（双轨取先）上一轮真实 prompt tokens > 100K（128K 窗口留 28K 余量）；或字符估算 > 500K
P1 预剪枝>200 字符的重复工具结果去重；>500 字符的老工具结果改写为一行摘要
尾部保护最近 6 条工具结果（≈3 轮调用）保留原文；尾部 100K 字符整体保留
压缩执行按切点丢弃 + 消息索引平移重建，压缩比可观测
对创作的含义（诚实标注）：压缩器意味着「早前读过的章节正文」在长回合中可能被压成一行——所以系统提示词要求的是查证纪律（写涉及主线事实前先 read/search，而不是依赖会话早段的记忆）。一本番外通常 1~5 章，实际很少触发压缩。尚未做的前情摘要提取（对长篇自动生成每章摘要供低成本回看）是已评估的后续改进项。

命名空间隔离核对表：番外 vs 正篇，会不会读错？

「读错命名空间」是番外体系最致命的故障模式。逐通道核对代码实现——每个工具的上下文来源、最终指向、以及靠什么机制保证不串：

通道上下文来源指向隔离机制
read / search / list_chapters / list_characters（主聊，创作番外全程）currentNovelId（保持宿主不变）宿主（查证通道）create_side_story 不切换工作小说——查证通道零成本且永不指错
create_side_storyReadingContext（当前阅读章）或 anchorChapterPosition建番外隐藏行幂等查库（锚点+需求）；递归锚点=父番外 URL
save_side_story_chapterctx.sideStoryWritingTarget（会话记录的番外 id）番外命名空间显式目标 + saveChapter 五道闸门；无目标 → no_side_story 安全失败，绝不触碰宿主
save_chapter / update / rewrite / deletecurrentNovelId（宿主）正篇命名空间番外在所有小说列表被 isSideStory=0 过滤、select 不到——正篇写工具永远够不到番外
核对结论（v2 架构复核）：番外三工具 + 主聊全部通道逐一过——不存在「番外读到正篇、正篇读到番外」的路径。写入隔离靠「显式目标」：save_side_story_chapter 没有目标时只会安全失败（no_side_story），save_chapter 系工具经 currentNovel 只触达正篇（番外不可 select）——两个方向都无静默错。
诚实标注遗留点：① save_side_story_chapter 的 position（番内序号）与 read 的 position（宿主序号）同名不同义——schema 已显式澄清，仍是认知负担；② 暂无「读番外自己已保存章节」的工具（正文在回复历史里，通常够用；极端场景可用 list_side_stories 看章数）；③ 主聊无「打开旧番外继续改」的直达工具——通过重新 create_side_story（同锚点同需求幂等找回）续写。
05

数据模型：一条隐藏行，两个命名空间

番外不建独立表体系——它就是一条 bookshelf 隐藏行 + 该行 novelUrl 命名空间下的普通章节行。章节列表页、阅读器、版本历史、备份全部零改动复用。

宿主小说《搭讪就有奖，加满5000个好友》 bookshelf 行（isSideStory=0，书架可见）
├─ 第 1 章 …… novel_chapters（宿主命名空间）
├─ …
├─ 第 200 章 女主与闺蜜重逢 ← 锚点章
│ └─ 番外《闺蜜往事》 bookshelf 行（isSideStory=1，书架过滤不可见）
│ ├─ URL: custom://sidestory/<微秒时间戳>
│ ├─ anchorNovelUrl → 宿主 URL　anchorChapterUrl → 锚点章 URL
│ ├─ description = 用户需求（幂等查库依据 + 列表页展示）
│ ├─ 第 1 章 初遇 …… novel_chapters（番外命名空间）
│ ├─ 第 2 章 分离 ……
│ │ └─ 番外《分离之后》 ← 番外再挂番外（递归，层数不限）
字段语义
isSideStory = 1隐藏标记：书架三类查询、全库小说列表、来源域查询统一加 isSideStory = 0 过滤——番外对书架完全隐身，但备份/恢复自然携带
anchorNovelUrl宿主小说（主线或父番外）的 URL——递归因此免费获得
anchorChapterUrl锚点章 URL；锚点章被删除/重排后番外保留，列表显示「原章节已移除」（不做静默删除）
description用户需求原文——既是列表页展示，也是 create_side_story 幂等查库的依据
custom://sidestory/<ts>URL 用微秒时间戳 + 探测去重（撞 UNIQUE 约束时追加 _N 后缀重试）
已读进度 / 继续阅读：复用 novel_chapters.readAt + bookshelf.lastReadChapter（按番外自身 novelUrl），零额外开发。
06

落库防线：save_side_story_chapter 的五道闸门

save_side_story_chapter 是哑工具——不生成任何内容，只校验与落库（内部完全复用 save_chapter 的校验链）。所有垃圾内容在写进数据库前被拦下，拦截时返回引导错误（错误码 + 怎么改），模型一轮自纠。

① position_out_of_range position 必须 ≤ 番外现有章节数 + 1；越界时引导先确认已保存章数 拒写
② 转义还原 unescapeJsonEscapeSequences：模型透传的字面 \n / \" 序列还原为真字符（防「字面转义落进正文」） 清洗
③ JSON 污染检测 2026-11-15 detectJsonContamination 四规则：整体即 JSON / 围栏 JSON / 独立行工具回声 / 值内嵌键值对（反馈 #16 实际故障形态）——命中即拒写，正文必须是纯文本散文 拒写
④ markdown 净化 ContentSanitizer：剥 ``` 围栏、**粗体**、# 标题、> 引用等标记，保文字——阅读器里永远看不到原始符号 清洗
⑤ content_too_short 低于 300 字 = 回复被截断或偷懒，拒保存并引导完整重写（正常章节 1500~3000 字） 拒写
⬇ 全部通过 ⬇
ChapterMutation.createChapter 单事务 shift+insert 落库进番外命名空间（原有章节自动后移）+ 信号广播；返回 chapterUrl 驱动「查看新保存的番外章节」跳转卡 入库
同一防线覆盖三个写入通道：save_chapter（正篇新建）、save_side_story_chapter（番外新建）、update_chapter_content（正篇局部替换——检测只查模型增量 newString，oldString 与全文绝不检测，否则历史污染永远修不掉）。规则来自真实故障样本（反馈 #16 的 LLM 调用日志），误伤防线有专项测试：正常对话、程序员题材内嵌 {"a":1}、```text 围栏散文全部放行。

删除与级联

  • 删除单个番外：列表页长按/菜单 → 确认框 → 单事务删除番外行 + 其命名空间下全部章节/缓存/版本/标注
  • 删除主线小说：级联删除其全部番外（含番外的番外——递归收集 anchorNovelUrl 链，环路安全）
  • 锚点章被删/重排：番外保留，锚点显示「原章节已移除」
  • 备份/恢复：番外随 bookshelf/chapter 表自然进出备份
已知改进项（待办）：① 对既有长篇做前情摘要提取（每章自动摘要供低成本回看，替代「Agent 自选章节去读」）；② B 修复：thinking 模型的 reasoning_content 回传（每轮 3 次 400 重试 + 退避，影响所有 AI 写作耗时）——已定位待实施。
