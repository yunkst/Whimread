写作 Agent 重构计划 v2场景修正版：主场景不是从零写小说，是在「已经写成的小说」上做衍生创作（番外）

一句话版本

我们的主场景：一本已经成型的小说（多为导入的网文，章节已缓存本地），读者在某一章触发番外创作。此时大纲已存在（章节列表就是大纲）、事实已存在（正文就是设定源）、结构不需要创造。所以 v1 照搬 Dramatron / NovelCrafter 这些「从零写作」框架的结论——让 Agent 边写边攒大纲、beats、人物进展——方向错了，那是在给「从零写」补结构。番外场景缺的是理解力：低成本读懂既有正文，再忠实延续。v2 把「累积式记忆」翻转成「提取式理解」：摘要与人物状态不是 Agent 写出来的，是系统从既有正文里提取出来的。

v1 → v2 修订说明（场景纠偏）：v1 误把「原创长篇连载」当主场景。实际受影响项—— P0-1 摘要（Agent 随写随攒 → 管线从既有正文提取）、 P1 人物进展（记录变化 → 提取现状）、 结构化 beats（v1-P1-2）→ 删除（番外结构已存在，归入「原创模式」独立 track）、 审校环 P2 → 升 P1（与主线不打架就是番外的第一质量指标）。 不受影响项：注入层、save_chapter 阶段 0 成果、工具瘦身。
阶段 0 已完成：save_chapter 重构已落地——正文由 Agent 在会话内直接写出、哑工具落库，消灭了旧 create_chapter「内层独立 LLM 调用只靠一句 instruction 传上下文」的失忆根源。本计划构建在它之上。

02

诊断：细节错乱的根源是「既有内容不可理解」

v1 的诊断是「系统把记住一切的责任压在工作记忆上」——这对原创续写成立，但番外场景要改写成：系统没有把「既有小说」变成 Agent 可理解、可查证的数据。工作记忆有限是常态，前提是得给它一条接触既有事实的路。

👉 一个真实的失败瞬间 用户在第 200 章创建番外：「女主与闺蜜的十年前」
Agent 调 read_chapter_content ✓（只有第 200 章，锁死）
Agent 调 list_chapters ✓（300 个标题，无内容）
Agent 调 list_characters ✓（导入的网文：人物卡为空）
闺蜜在第 3 章登场、第 45 章与女主决裂出国、口癖是「啧」、左腕有旧伤——全在 Agent 看不见的章节里
写出的番外：闺蜜「温婉可人、与女主从未红过脸、十指完好」——与主线第 45、102 章直接矛盾
长回合中，压缩器把仅有的锚点章正文也压成一行（只保护最近 6 条工具结果）
#缺陷对番外质量的直接伤害
1既有正文不可及——read_chapter_content 锁死锚点章，全书其余章节没有任何读取通道番外与现实脱节，只能围绕锚点章「编」
2无摘要理解层——300 章的事实只以「标题列表」形态存在无法低成本通晓前情，长程设定全部丢失
3人物事实无人提取——人物卡是静态档案且对导入小说常为空；口癖/旧伤/关系变化没有提取管线OOC、人物状态与主线脱节
4system prompt 零自动注入——连锚点章都要靠流程约定让 Agent 自己调工具去读忘查一次、或结果被压缩，就凭空编一次
5search_in_chapters 不在番外工具面——精确查证既有事实的最后一条通道被关掉长尾疑问（某配角、某物件）无路可查
6无一致性校验——写完即完成与主线的矛盾只有读者能发现
7压缩器只护最近 6 条工具结果长回合中锚点章正文同样被压掉
03

目标架构：围绕「衍生创作」重组五层

v1 的五层是「从零写作」的五层（含结构层）。番外场景的结构已经存在——主线的章节序列就是结构。所以 v2 把「结构层」从架构里有意去掉，换成「理解层」：系统预先从既有正文提取可检索的事实，注入层负责送进上下文，检索层兜住长尾疑问，校验层保证不打架。

🧠 理解层 ← P0-1 从既有正文**提取**章节摘要 / 关键事实 / 全书梗概 —— 管线批量生成、缓存 DB、不占 Agent 工具面 P0 新建
💉 注入层 ← P0-2 system prompt 确定性装配：锚点章全文 + 邻章摘要 + 人物 digest + 全书梗概 P0 新建
🔎 检索层 ← P0-3 search_in_chapters 加入番外白名单 + 新增 get_chapter_summary + read 解锁全书缓存章 P0 补齐
✍️ 写入层 ✓ 已有 save_chapter（阶段 0 重构完成：会话内写作、哑工具落库） 已具备
🛡 校验层 ← P1-2 reviewer 对照提取事实清单审校番外正文 —— 矛盾在入库前被拦，而非被读者发现 P1 新建（v1 排 P2，场景纠偏后升级）
为什么没有「结构层」：beats / 大纲规划只对「从零写」有意义——番外的每一章该挂在那条支线上、起承转合如何，是由 Agent 根据需求与锚点现场决定的，不需要预设的任务卡。原创长篇连载如需 beats / 累积式记忆，归入「原创模式」独立 track（见 P2-2），不混入番外的精简工具面。
04

计划详解：五项改动与各自的「提效机制」

每一项都回答三个问题：做什么、为什么能提升创作效果（机制链）、参照了谁。改动集中在 services/novel_agent/ 与一张新表，不动 UI。

P0-1

章节理解层 —— 从既有正文提取，不是随写随攒

参照：RAG 检索增强 / RecurrentGPT 长期记忆（方向反转：提取「别人写完的」）
  • 做什么：新表 chapter_summaries（novelUrl / chapterUrl / position / summary / keyFacts / characters / updatedAt）。由确定性管线（代码发起的小型 LLM 调用）生成，不进 Agent 工具面：番外场景启动时懒生成锚点章 ±N 窗口，随后后台逐章补全；章节被改写时失效重提。
  • keyFacts 即一致性锚点：人物状态（受伤 / 获得物 / 死亡）、关系变化、时间点、伏笔承诺——正是细节错乱的四大来源。
  • 边界：只覆盖已缓存章节；未缓存章在索引中标注「未缓存」，Agent 可提示用户先加载。成本集中一次性，之后永久缓存复用。
为什么能提升创作效果　 300 章不可读→300 条可检索的结构化事实→「闺蜜哪章决裂」一次查询就有出处→事实有出处，编造无处遁形→番外与主线的兼容性从「碰运气」变成「有下限」
P0-2

确定性上下文注入 —— 番外的 system prompt 自带前情

参照：NovelCrafter Codex 自动注入（差异：Codex 靠作者手填卡，我们全自动提取）
  • 做什么：side_story 场景 buildSystemPrompt 直接装配四样：锚点章全文（Agent 不必再调 read）、锚点前后各 1~2 章摘要、主要人物 digest（P1-1 后接入，先接人物卡）、全书一句话梗概（由摘要分层聚合：分卷摘要 → 全书梗概）。
  • 长度预算：锚点章全文封顶（如 6000 字）、邻章摘要各 200 字、人物 digest 按与需求的相关度挑选——宁可精，不可爆。
  • 原创写作场景同样适用：注入其大纲 / 人物卡 / 前一章结尾，机制相同、数据源不同。
为什么能提升创作效果　 上下文从「流程约定 + Agent 自觉」→「system prompt 必然存在的固定区」→零遗漏、不会被压缩器吃掉→锚点衔接与人物口吻从第一段就锁定→「忘查就瞎编」整类错误消失
P0-3

番外工具面补齐 —— 把查证通道还给 Agent

内部补齐（现有 executor 直接复用）
  • 做什么：① search_in_chapters 加入番外 7 工具白名单（全文精确查证，executor 现成）；② 新增 get_chapter_summary(chapterUrl | position)——读摘要级前情，比全文便宜两个数量级；③ read_chapter_content 解锁为「宿主任意已缓存章」（锚点章保持默认），不再锁死单章。
  • 原则：注入层覆盖「大概率需要的前情」，检索层兜住「长尾疑问」——两层互补，长尾不再靠编。
为什么能提升创作效果　 注入管「常考题」→检索管「偏题」→任何一处既有事实都「查得到、读得起」→Agent 敢写不熟悉的配角与远期设定→番外题材范围从「锚点章周边」扩展到「全书任一支线」
P1-1

人物状态提取 —— 提取「她现在什么样」，不是记录「她变了什么」

参照：NovelCrafter progressions（场景反转：对既有小说是提取，不是记录）
  • 做什么：从 chapter_summaries 聚合 per-character 状态卡：现状 / 关系网 / 所在位置 / 口癖 / 旧伤，每条标注出处章号；接入 P0-2 的人物 digest 注入；list_characters 返回时附提取状态（无卡时明确说明，而非静默空列表）。
  • 与 v1 的区别：v1 是「Agent 写完一章登记一条 progression」——只对原创模式成立；导入的网文几百章没人登记过，必须反向提取。
为什么能提升创作效果　 人物 digest 带着「第 45 章已决裂、左腕旧伤未愈」→生成前矛盾就被拦住→而非写完后被读者发现→OOC 类差评整类下降
P1-2

一致性审校环 —— 番外的第一质量指标是「与主线不打架」

参照：CreAgentive writer–reviewer 反馈环 / Re3 修订环
  • 做什么：dispatch_subagent 配 reviewer 只读白名单（摘要 / 检索 / 锚点正文）+ 一致性 checklist（人物状态 / 时间线 / 称谓地名 / 已死角色）；每本番外保存完跑一次，发现问题回注主 Agent 修订（rewrite 通道现成）。
  • 为何从 v1 的 P2 升到 P1：原创连载的核心诉求是「越写越不漂」，审校是锦上添花；番外的核心诉求就是与既有事实一致——审校在这里是刚需，不该排队。
为什么能提升创作效果　 错误的发现者从「读者评论区」→「发布前的 reviewer」→矛盾在入库前被拦→修订成本从「删番外重来」降到「改一段」→番外可信度 = 用户敢持续用这个功能
P2

工具瘦身 + 「原创模式」独立 track —— 两类场景分道扬镳

内部优化
  • 做什么：① 创作回合（writing / side_story）工具面收窄到 ~15 个创作相关工具，生图与文字游戏系移出；② 从零原创长篇作为独立 track 后续增强：累积式摘要（save_chapter_summary）、人物进展记录、结构化 beats——这些只对「边写边攒设定」的场景有意义。
  • 收益：番外的精简工具面不被原创功能污染；原创场景的规划能力不受番外约束。
为什么能提升创作效果　 schema 从 31 份 → 15 份→工具选择错误率下降、每轮省数千 token→同样的上下文窗口装下更多正文与前情→两个场景各自演化、互不拖累

06

外部案例：同一批框架，换一个场景读法

v1 曾把这些框架当作「直接抄作业」的模板——它们确实优秀，但都是从零写作的范式。放在「既有小说 + 衍生创作」场景下，有的机制要反转方向用，有的要降级移走。逐个过一遍。

体系核心机制对我们场景的启示
RecurrentGPT 语言版 LSTM：短期记忆（近期上下文）+ 长期记忆（可检索摘要库）同步更新 P0-1 理解层 —— 但方向反转：它攒「自己写的」，我们提取「别人写完的」；导入的网文没人替它攒，只能自动提取
NovelCrafter Codex 故事圣经：实体卡自动注入 + 进展记录（progressions） P0-2 注入 + P1-1 状态提取 —— Codex 的卡靠作者手填；我们的用户是读者不是作者，必须全自动提取
CreAgentive（2025） writer–reviewer 多 agent 反馈环，百万字级长文生成 P1-2 审校环 —— 在衍生创作中一致性权重最高，所以从 P2 升 P1
Re3 递归重提示 + 修订：草稿 → 重写 → 编辑循环 P1-2 的另一种形态；rewrite_chapter 已是现成的修订通道
Dramatron（DeepMind） 层级提示链：logline → 人物 → plot beats → 场景 降级移走 —— beats 是「从零规划」的产物；番外的结构（主线章节序列）已存在。归入「原创模式」独立 track
Sudowrite Story Bible braindump 引导式构建故事圣经 同上 —— 引导用户「建设定」只适合原创场景，远期参考
RAG（检索增强生成） 先检索相关语料再生成，事实有出处 P0-3 检索层 —— 番外本质是对既有语料的受控衍生，检索兜住注入层覆盖不到的长尾
07

路线图与验收标准

P0 三项是「给番外装眼睛」（先能看见主线），P1 两项是「保证不打架」（状态提取 + 审校），P2 是「分道扬镳」（瘦身 + 原创模式独立 track）。每项带可验证的验收标准。
